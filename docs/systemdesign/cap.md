title: CAP 理论与分布式基础
---

## 1. CAP 定理

- **C** (Consistency) — 所有节点看到相同数据
- **A** (Availability) — 每个请求都能得到响应
- **P** (Partition Tolerance) — 网络分区时系统继续运行

::: warning 核心结论
网络分区不可避免（P 是必选），只能在 C 和 A 之间选择。CA 只存在于单机系统。

| 选择 | 牺牲 | 典型系统 |
|------|------|----------|
| CP | 可用性 | Etcd, ZooKeeper |
| AP | 强一致性 | Cassandra, DynamoDB |
:::

## 2. BASE 理论

- **BA** (Basically Available) — 故障时允许响应时间增加或功能降级
- **S** (Soft State) — 允许数据存在中间状态
- **E** (Eventually Consistent) — 最终所有副本数据一致

BASE 是对 CAP 中 AP 方向的补充，是大多数互联网系统的实际选择。

## 3. 一致性模型

| 模型 | 保证 | 代价 |
|------|------|------|
| 强一致性 | 任何时候读到最新值 | 高延迟（多数派确认） |
| 最终一致性 | 一段时间后一致 | 可能读到旧数据 |
| 因果一致性 | 有因果关系的操作有序 | 实现复杂 |
| 读己之写 | 写入后立即能读到 | 需要写主读主 |

## 4. 分布式 ID 生成

| 方案 | 特点 |
|------|------|
| Snowflake | 时间+机器+序列号，趋势递增 |
| Leaf | 号段模式/Snowflake，美团 |
| UUID | 无序、长度长 |
| Redis INCR | 简单、依赖 Redis |

Snowflake 64 bit：`1bit(0) | 41bit(时间戳,69年) | 10bit(机器ID,1024) | 12bit(序列,4096/ms)`

::: tip 时钟回拨问题
NTP 同步可能导致时钟回拨。解决：等待追平 / 拒绝生成 / 使用历史最大时间。
:::

## 5. 实际系统取舍

- **金融系统** → CP（宁可不可用也不能数据错）
- **电商系统** → 混合（下单 CP，搜索 AP）
- **社交系统** → AP（帖子/评论最终一致可接受）

核心原则：不是所有数据都需要强一致，根据业务特点选择合适的一致性级别。
